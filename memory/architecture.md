# Architecture and design constraints

## Purpose and composition

The project composes four NixOS systems: `nixos` (ThinkBook), `nixos-matebook`, `nixos-server` (Aliyun) and `nixos-wsl`. Its goal is selectable shared capabilities across distinct hardware and environments, with finer ownership than a monolithic Home Manager profile.

The original uniform descriptor and discovery protocol supported explicit selection and fine-grained sharing. Its common shape obscured differences in the responsibilities, cardinalities and deployment relationships of Hosts, Users, Features, Workloads and Share. Validators rejected some shapes that the constructor could have excluded, and an adapter mirrored FP data into native configurations. Phase one stabilized native Feature implementations and child exports. Phase two replaced the root composition model directly, with no committed compatibility stage. The owner retained one globally readable FP option space. Distinct schemas express domain responsibilities and let construction enforce cardinality and bindings directly. Feature and Workload share selection machinery while keeping separate namespaces. Workloads may eventually describe cross-Host deployment and cooperation. Base provides shared infrastructure for every System. Add a generic System- or Account-level deferred module interface only for a demonstrated need.

## Construction semantics and layer boundaries

Root declares `nixosBuilderArgs` and `nixosConfigurations` through `llib.flakeParts.mkOptions config`. `llib.flakeParts.mkNixosConfigurations { builderArgs; configurations; }` produces `flake.nixosConfigurations`. Builder arguments include `nixosSystem`, explicit `homeManager`, `baseModule`, shared `specialArgs`, the Host and User registries, derived read-only `hostTopology`, `featureRegistry.{os,hm}` and `workloadRegistry`.

A System selects one Host directly and declares OS Features, Workloads and UID-keyed Accounts. Host and User entries have distinct typed FP submodule schemas, with `module` as a deferred native module alongside their domain fields. Each entry's read-only `name` derives from its Registry key. A `host` or `profile` selection is unique and resolves by that name in the final Registry. Passing the Registry entry is the normal notation. Other fields supplied in a reference have no override semantics.

OS and HM Feature selections and Workload selections have default-off `enable` and a mergeable deferred `module`. An enabled selection imports its registered implementation, its consumer module and an explicit native enable definition. A disabled selection imports neither implementation nor consumer module. Another selected implementation or Base can still import a shared dependency. Dependency declarations in the lock graph and package presence in a closure are separate from native module selection. OS and HM are selected independently. Native Features may read other Features' options, including through `osConfig`, and assert dependencies, but must not enable, import or configure other Features. FP consumer modules can configure multiple selected components.

The constructor adds the selected `host` and `hostRegistry` with entry `module` fields removed, plus `hostTopology` and UID-keyed `accounts`, to the common OS `specialArgs`. The Account projection omits Feature selections and the Profile's native module and Feature fragments. HM receives common arguments and its normal `osConfig`. The constructor transfers the data needed for assembly and binds Accounts to the Host. Feature-specific decisions belong to the contributing modules. There is no native mirror of the FP option space. Each Host declares `nixpkgs.hostPlatform`, and the constructor passes `system = null` to `nixosSystem`. Flake-parts `systems` governs per-system outputs separately.

## Module directory interface

Root `flake.nix` initializes the framework, composes external inputs and outputs, and declares System selections. `modules/default.nix` explicitly imports the `base`, `hosts`, `users` and `workloads` aggregators. Their FP modules contribute to the global option space, with ordinary `modules/<kind>/<name>/default.nix` entries and native code under `os/` or `hm/`. Domain declarations and wiring live in explicit modules such as `modules/hosts/options.nix`, `modules/users/options.nix` and the Greeter and Niri FP entries. Keep external input references in the owning flake and organize imports without parent-relative paths. Package and test discovery retain their own loaders.

`modules/base/default.nix` adds the local OS and shared HM modules to `baseModule`. Base OS provides boot manager, Bluetooth, NetworkManager, power, identity, secret delivery, SSH targets and WireGuard configuration. Host-owned policy for boot manager, Bluetooth, NetworkManager and power is declared through native `base.<name>.enable` options. Base declares and consumes these internal, read-only options without explicit defaults. The owner preferred explicit enable values to import-only templates, and accepted that disabled Base modules can omit their own contributions while other modules may enable an upstream service. This moved `shared` and `bootManager` policy out of the Host Registry. Identity remains Registry data because it is reused across Host, Profile and Account references. Root adds Home Manager and the shared upstream integrations explicitly. HM uses `useGlobalPkgs = true` and explicit base shared modules. Base declares `xdg.createUserDirectories` and projects it to HM directory settings. Package allowances use `nixpkgs.config.allowUnfreePackages`.

Both flakes assemble their outputs with the personal-nixpkgs `mkFlake` wrapper and pass the required local library arguments. The root builder's common arguments are `llib` and `rootPath`. The child uses its own `llib` and `lpkgs`. Flake-parts and treefmt-nix are owned through the personal-nixpkgs inputs.

## Native Feature implementations

Every native OS or HM Feature implementation declares its own default-off `features.<name>.enable`. Importing the module makes its options available in that evaluation scope. Its native enablement controls configuration contributions. Root FP modules under `modules/features/<name>/default.nix` register local implementations under `modules/features/<name>/{os,hm}/`. Root combines these registrations with child upstream integrations in `flake.nix`. The child owns the Nixvim and Niri inputs and exposes upstream modules and overlays; native Feature modules accept actual package values. The root Base consumes the existing child `overlays.share`, `nixosModules.share` and `homeModules.share` exports as common dependencies.

Generic native connections supply defaults for their own options. Greeter derives its session packages from enabled providers, with Niri preceding X11. File-manager HM derives its FileChooser default from the OS File-manager Feature and its FileChooser state, and its Wayfile default from the current HM Niri Feature. OS Noctalia and OS FileChooser default to their owning Feature's enablement. Niri HM defaults Noctalia from OS Niri and OS Noctalia and defaults Waybar on when HM Niri is enabled without Noctalia. HM Shell reads OS `features.shell.{bash,zsh}.package` and native Zsh state. Internal wiring and outputs such as monitors and session packages are read-only where there is one owner. Keep business option types, merge behavior and real dependency assertions with their native consumers. A matching Feature name alone does not establish an HM-to-OS enable dependency. Required service and operating-state checks remain native.

## Users and interfaces

A User Registry profile describes reusable personal environment and data. The presence of a System's `users.<uid>` entry constructs the Account. It selects a `profile`, `username`, `homeDirectory` (default `/home/${username}`) and independent HM Features. Its schema exposes account identity, profile binding and HM selections. Native Feature customization goes through the selected consumer module. The Host owns UID reservations and machine authorization. The Account binds a registered UID to its login name and home. Both native account maps use canonical decimal UID strings as keys, and the constructor projects identity using the existing force semantics. Spare Host UID reservations are valid.

Profile-local configuration is carried in sparse read-only `features.<name>.module` entries without a default. An entry uses `llib.types.deferredModuleFragment`, which keeps callable values and normalizes plain attrsets to constant functions at a single-definition merge. `llib.modules.mapModule` preserves function argument declarations and applies the caller's transformation to the result. Only the Feature-specific `mkFeatureModule` specialization places values under `config.features.<name>`. Account FP composition merges that contribution into the Account's deferred module for the corresponding Feature without changing selection. Each Account evaluates the selected contribution in its own native HM environment. This keeps business schemas with native consumers and keeps the constructor generic. The fragment interface supplies neither a separate module system nor security isolation or origin tracking.

## Host facts and graphics

Hosts own stable numbers, UID reservations, authorization, identity, machine resources, WireGuard facts and monitors. Greeter and Niri own their FP monitor connections. Greeter receives the complete default Monitor and HM Niri receives the Host monitor set. A selected Greeter requires a default monitor through its consumer module. HM Niri checks the requirement with its native assertion. A Host without monitors can be valid, including with OS Niri selected. SSH identity lives under `identity.keys`. Root access is separate authorization policy.

## Desktop and native capabilities

Niri remains the main native desktop and starts Noctalia v5 from HM settings. OS Noctalia configuration supplies recommended services without installing its own competing user launch path. Noctalia now owns normal/idle/pre-suspend locking; swaylock remains an allow-when-locked rescue path. One login_box is centered on the default monitor using mode/scale-derived logical dimensions, with weather false and unlock hint true. Custom clock/weather trials were withdrawn; earlier successful migration checks do not verify this final lockscreen stage. Other outputs remain locked; runtime settings may override declarative values.

Greetd's temporary Sway/gtkgreet and the independent IceWM/startx fallback retain separate session duties. Browser reuse across concurrent sessions remains a historical unresolved report. Native xdg.terminal-exec supplies terminal capability; Yazi/Wayfile handle directories and the independent FileChooser portal only affects clients using it. ThinkBook framebuffer initialization is a host-gated oneshot/udev path; kmscon ownership proposals remain unadopted.

## Secrets and agent inputs

Agenix and Agenix-rekey are Base infrastructure. The dedicated rage-armored wrapper supports text-only encrypted retention. Master identities unlock repository sources, Host public keys encrypt deployment ciphertexts, and preinstalled Host private keys unlock deployment ciphertexts at runtime.

Host and User Profile share the optional age and SSH key schema. Host retains its own `rootAccess` policy. Base OS derives User age identity delivery from UID-keyed Account bindings without a Feature selection. `llib.identity.userAgeSecretName` derives the native secret name from the UID. Agenix supplies the resolved install path, with an optional explicit path override that must avoid collisions. The Account owns its installed User age identity with group root and mode `0400`. User SSH identity has no current delivery wiring.

The owner retained the HM declaration scope so Profiles can declare the secrets their environment needs. Base OS delivers the final application secrets through Agenix. User identity remains useful independently of those secrets. The recursive HM `secrets` option identifies leaves by `rekeyFile` and exposes a read-only `path` derived from native OS `age.secrets`. Modules can merge branches; empty branches produce no secret. Names are validated, and leaves cannot also be branches. OS traverses only the raw declarations and names entries by UID and dot-separated tree path. It must avoid reading HM's derived path, which depends on the OS declaration it is creating. OS delivers each secret with the Account username as owner, group root and mode `0400`. The tree organizes declarations and names independently of ciphertext layout. Lingyu declares its application secrets under `hm/secrets/`. Rclone and the Pi providers consume `config.secrets.<...>.path`; Agent's provider interface accepts a path independently of any particular secret backend.

The original OS-to-HM shared age bridge was transitional. During the migration, independently delivered User identity briefly supported HM SOPS after the OS SOPS Feature was removed. The owner observed that HM SOPS could run before OS Agenix delivered the User identity, and chose to retire that user-side decryption path without adding ordering for it. This leaves the timing of actual consumers a separate verification question. The attempted User identity rotation was withdrawn. The OS-backed HM secret tree then replaced the SOPS delivery path, existing consumers were migrated, and SOPS and its legacy files were removed. The former bridge, SOPS-specific authorization and enable dependencies are historical.

`modules/base/os/identity.nix` registers the selected Host's non-null SSH identity backup as an Agenix intermediary. Registration is independent of `rootAccess`, which gates YubiKey tooling and pcscd. An intermediary participates in source master-key management. Host rekey skips its backup payload and installs a dummy secret. Backup decryption therefore requires separate verification. Master identity lifecycle ownership and recovery follow-ups remain in [backlog.md](backlog.md#independent-follow-ups).

## Library and verification

`lib/flakeParts.nix` owns the shared FP schema and constructors. `validateAccounts` is internal to construction. `lib/hosts.nix` owns topology, networking and SSH derivation. Libraries receive their actual dependencies individually. Shared Monitor, identity, default-editor and deferred-fragment types live in root `lib/types.nix`. `lib/modules.nix` maps fragment arguments and results; `lib/identity.nix` and `lib/secrets.nix` provide naming and secret tree support.

`tests/configurations` exercises constructor behavior, schema extension and merge, selection cancellation, unforced unselected deferred modules, independent Accounts, binding invariants, cross-Host and System references, and project connection modules. Host-function checks cover topology, peers, routing, FORWARD isolation, generated OUTPUT policy and SSH aliases. Root also has native-enable, module-mapping and secret-tree checks. The latter checks mocked delivery paths, Account isolation, declaration merging and invalid node shapes. Suites use `llib.tests.mkChecks` and `test-overlay.nix` with explicit dependency injection. `tests/default.nix` selects which library namespaces and other dependencies to inject. Treefmt remains part of flake checks. Verification results and their source boundaries are in [current.md](current.md).

## Network ownership

Host topology is derived in FP from the Host Registry using `wireguardRules`, `mkWireGuardNetworkData` and `mkWireGuardTopology`. Base OS projects it into the existing read-only `networking.wireguard.topology`. `mkWireGuardNetworks` takes an explicit `hostName` and returns native networking configuration directly. Its callers obtain topology separately. Hosts own encrypted WireGuard material and stable numbers. One network is derived per endpoint Host. Topology keys are Hub and node Host names, with each Hub's interface, subnet and node IPv4 addresses. Peer roles are per network. Each Hub gives spoke peers individual `/32` AllowedIPs, each spoke routes the network subnet through the Hub, and endpoint Hosts enable IPv4 forwarding. The `wireguard-isolation` FORWARD chain allows IPv4 forwarding within the local Hub's own interface and drops other forwarded traffic involving managed interfaces. Keep this separate from local OUTPUT policy.

SSH targets consume the same topology for system-wide `<hub>.<node>` client aliases. Paths to the same Host share a trusted host key identity. See [current.md](current.md#wireguard-ssh-targets-and-aliyun-reachability) for the historical Aliyun reachability diagnosis.

Hosts explicitly set the internal read-only `base.wireguard.firewall.restrictOutput`. Aliyun opts into default rejection for local OUTPUT on its managed WireGuard interfaces. The other Hosts opt out. Base derives the managed interface set from topology membership and emits a table only when the restriction is selected and the set is nonempty. Reply-direction established traffic and related reply ICMP/ICMPv6 traffic are allowed before explicit business authorizations and the final reject. Native modules contribute those authorizations through `base.wireguard.firewall.extraOutputAllowRules`, a mergeable `types.lines` option. Hub status and Workload activation do not decide Host policy. This interface covers managed WireGuard networks.

## Definition ownership

Define basic shape and validity with types, local and collection invariants with option `apply`, function preconditions where the function consumes them, and final native-state constraints with native assertions. Read-only options constrain raw definitions. Unique types constrain value merging. Give derived facts a clear producer and put fallback interpretation in their consumers. FP modules can extend nested Registry and System/Account schemas and contribute deferred modules using values they own.

## Workload responsibilities

Workloads are explicitly selected native implementations with `workloads.<name>` options. Deployment-specific IPs, ports, interfaces and access values come from FP consumer modules. Root wires Caddy on Aliyun to WBO on ThinkBook at port 18000, with the allowed source and interfaces supplied from FP topology. The native WBO port is required. Caddy contributes a Host allowance for its socket UID and designated TCP upstream. Its independent OUTPUT table matches only that UID over all managed WireGuard interfaces, allows the reply exceptions and the designated upstream address, TCP port and interface, and rejects other matching traffic. The table applies independently of Host default rejection. Newly managed interfaces grant no additional initiation rights. Replacing the old interface-wide reject narrowed Caddy's policy to its own UID and removed Caddy's reject for other UIDs. The Host policy still applies independently. Socket UID matching is a Caddy-specific principal choice with a scope narrower than a general network sandbox.

Keep Workloads portable by supplying explicit network endpoints and access requirements. A Workload can consume Host infrastructure, declare its own constraints and cooperate with other Workloads. Distinguish bidirectional data flow from an actual evaluation dependency cycle.

## Virtualization and host resources

ThinkBook integrates a declarative libvirt Windows guest through NixVirt, with domain/network/storage XML templates, GPU SR-IOV, guest tooling and Samba sharing. Display experiments return to SPICE after GTK trials; virtualized Windows is a host-owned workload/resource rather than another NixOS host profile. Mount policy distinguishes Windows and shared filesystems, with the Windows partition mounted read-only at this horizon. Static configuration does not establish a successful guest boot, GPU assignment, filesystem safety under every external OS or runtime display result.

## Local packages and tools

Package overlay.nix and test test-overlay.nix sources use an outer attribute-set constructor returning a standard Nixpkgs overlay, commonly {}: final_: prev_: {...}. The owner standardized the two overlay parameter names as final_/prev_; static comparison of the ten changed paths found only identifier/whitespace changes. The shared loader supplies only declared extraArgs/descendantOverlay constructor parameters and rejects other names. Returned overlays remain ordinary Nixpkgs extensions. Test mkChecks.args is the separate test-scope/callPackage dependency environment and is not constructor extraArgs. This is the committed constructor protocol; static source/documentation review does not establish successful checks of the constructor migration.

The pkgs/ child flake owns application input declarations, upstream integrations, overlays and recipes under pkgs/pkgs/. Its dependency versions for root consumption are recorded in root flake.lock; pkgs/flake.lock is no longer tracked. The committed .gitignore allowlist is anchored at the repository root; !/flake.lock permits only the root lockfile, while pkgs/flake.lock remains ignored by the default * rule. An unanchored !flake.lock would also permit child lockfiles. Standalone child use may produce a local lockfile, but the repository supplies no separate committed child lock baseline. Distinct root/child input declarations and versions do not require two committed lockfiles. Its personal-nixpkgs input supplies the generic library used as child llib.

The owner first placed native Features in the child flake to explore independent use. The implementations later returned to root when that boundary had limited value for the project. That move left input ownership and the lock graph intact. Root and child placement should follow actual independent use and versioning needs. Subsequent removal of SOPS changed the child input graph separately. See [backlog.md](backlog.md#subflake-boundary-exploration) for the unresolved alternatives.

pkgs/pkgs/default.nix requires only child llib and uses llib.packages for overlays and OS/HM module collection. The locked grouped-overlay API takes overlayFile = overlay.nix and two groups: legacy includes all local recipes with export = true, exposing pkgs.legacyPackages when applied; share excludes rage-armored. The default group/output is removed. Child outputs are overlays.legacy, overlays.share (local recipes except rage-armored, plus GAW/Lean), overlays.editor, overlays.niri, share OS/HM modules and the upstream Niri and Nixvim module integrations. Root local-nixpkgs references path:./pkgs. Root perSystem configures nixpkgs.overlays = [ inputs.local-nixpkgs.overlays.legacy ], consumes the mkFlake-provided pkgs, exports legacyPackages = pkgs.legacyPackages and shares pkgs with checks, devShells and agenix-rekey. The latter directly uses pkgs.rage-armored. The child no longer explicitly instantiates or exports legacyPackages in perSystem. Standalone child use has its own input declarations. When root consumes the child, the child Nixpkgs input follows root Nixpkgs. Root Base composes the share overlay and native share modules, and Systems and Accounts select root Feature registrations.

Root lib no longer owns package discovery. Pure customizations of upstream codex, difftastic and pi-coding-agent live directly in their overlay.nix files, reading upstream packages from prev_ and dependencies from final_; their former package.nix files are removed. Independently named packages retain their recipes, including rage-armored, and Wayfile also exposes a recipe directly consumed by its HM module. Package resources supply composable agent context and shared skills. Pi's offline startup wrapper preserves package layout; it does not prohibit model API networking. Codex's committed wrapper PATH includes bubblewrap plus Python/PyYAML support. Skill instructions do not replace execution authorization. Pi resource extensions and a historical proposed Git-action filter are different capabilities; the latter was not established as implemented by its source.

A historical child override redirected personal-nixpkgs's nested local-nixpkgs input to a Git source after the owner reported relative-path resolution against the process working directory. That workaround was removed. Root still consumes its own child via `path:./pkgs`.

The root lock pins the resolved child Emarccs input. The child manifest tracks its main branch and declares its follows edges. Desktop Emacs service packages use pkgs.emarccs-pgtk, while programs.package uses pkgs.emacs-pgtk; that updated service attribute has not been independently evaluated by the agent. Child lem, nixvim, git-agent-workflow and lean4-nix follow personal-nixpkgs/flake-parts. Root agenix-rekey and nixos-anywhere follow root personal-nixpkgs/treefmt-nix. Root enables treefmt.flakeCheck and excludes *.patch, .gitignore, LICENSE, README.org, flake.lock and *.age. Local explicit formatter-program declarations and direct treefmt module imports were removed during the mkFlake migration. The owner identified the five committed XML-template formatting changes as treefmt-generated; that report does not establish successful Nix checks. Root registers native-enable, module-mapping and user-secrets suites through the root test loader. This architectural description covers committed input declarations and lock state. The old Clash geodata/cache ambiguity remains an unconfirmed historical diagnostic, not a current verified failure or proven fix.

## Static constraint ownership

Host Registry `apply` checks global number uniqueness. Local `apply` checks monitor name uniqueness, at most one default with a mode, canonical UID keys matching their values, and WireGuard endpoint/listen-port consistency. Host number is a stable identifier and must be available to the Registry check without re-reading the final Registry through that same check. Local fields may read other entries. `checks.host-registry` explicitly forces constrained data for all Hosts, including unselected ones. Construction forces System selections and Account binding contracts, including UID registration, minimum Account UID 1000, unique login names and absolute home directories. Keep the remainder of the FP configuration and unselected deferred modules lazy.

The FP connection modules depend on the registered Feature names they extend. Removing an export requires adjusting its connections. Disabling a registered selection leaves those deferred contributions unimported. Keep native assertions for final dependencies such as Noctalia's actual services, Greeter's session packages, and Agent provider and terminal requirements. Neither construction checks nor flake checks alone establish deployed behavior.
