# Architecture and design constraints

## Purpose and composition

The project composes four NixOS systems: `nixos` (ThinkBook), `nixos-matebook`, `nixos-server` (Aliyun) and `nixos-wsl`. Its goal is selectable shared capabilities across distinct hardware and environments, with finer ownership than a monolithic Home Manager profile.

The original uniform descriptor and discovery protocol supported explicit selection and fine-grained sharing. Its common shape obscured differences in the responsibilities, cardinalities and deployment relationships of Hosts, Users, Features, Workloads and Share. Validators rejected some shapes that the constructor could have excluded, and an adapter mirrored FP data into native configurations. Phase one stabilized native Feature implementations and child exports. Phase two replaced the root composition model directly, with no committed compatibility stage. The owner retained one globally readable FP option space. Distinct schemas express domain responsibilities, and producers own the definitions they contribute.

## Construction semantics and layer boundaries

Root declares `nixosBuilderArgs` and `nixosConfigurations` through `llib.flakeParts.mkOptions config`. `llib.flakeParts.mkNixosConfigurations { builderArgs; configurations; }` produces `flake.nixosConfigurations`. Builder arguments include `nixosSystem`, explicit `homeManager`, `baseModule`, shared `specialArgs`, the Host and User registries, derived read-only `hostTopology`, `featureRegistry.{os,hm}` and `workloadRegistry`.

A System selects one Host directly and declares OS Features, Workloads and UID-keyed Accounts. Host and User entries have distinct typed FP submodule schemas, with `module` as a deferred native module alongside their domain fields. Each entry's read-only `name` derives from its Registry key. A `host` or `profile` selection is unique and resolves by that name in the final Registry. Passing the Registry entry is the normal notation. Other fields supplied in a reference have no override semantics.

OS and HM Feature selections and Workload selections have default-off `enable` and a mergeable deferred `module`. An enabled selection imports its registered implementation, its consumer module and an explicit native enable definition. A disabled selection imports neither implementation nor consumer module. Another selected implementation or Base can still import a shared dependency. Dependency declarations in the lock graph and package presence in a closure are separate from native module selection. OS and HM are selected independently. Native Features may read other Features' options, including through `osConfig`, and assert dependencies, but must not enable, import or configure other Features. FP consumer modules can configure multiple selected components.

The constructor adds the selected `host` and `hostRegistry` with entry `module` fields removed, plus `hostTopology`, to the common OS `specialArgs`. HM receives common arguments and its normal `osConfig`. The constructor transfers the data needed for assembly and binds Accounts to the Host. Feature-specific decisions belong to the contributing modules. There is no native mirror of the FP option space. Each Host declares `nixpkgs.hostPlatform`, and the constructor passes `system = null` to `nixosSystem`. Flake-parts `systems` governs per-system outputs separately.

## Module directory interface

Root `flake.nix` initializes the framework, composes external inputs and outputs, and declares System selections. `modules/default.nix` explicitly imports the `base`, `hosts`, `users` and `workloads` aggregators. Their FP modules contribute to the global option space, with ordinary `modules/<kind>/<name>/default.nix` entries and native code under `os/` or `hm/`. Domain declarations and wiring live in explicit modules such as `modules/hosts/options.nix`, `modules/hosts/features.nix` and `modules/users/options.nix`. Keep external input references in the owning flake and organize imports without parent-relative paths. Package and test discovery retain their own loaders.

`modules/base/default.nix` adds the local OS and shared HM modules to `baseModule`. Base OS provides boot-manager, identity, shared resources, SSH targets and WireGuard configuration using Host data. Root adds Home Manager and the shared upstream integrations explicitly. HM uses `useGlobalPkgs = true` and explicit base shared modules. Base declares `xdg.createUserDirectories` and projects it to HM directory settings. Package allowances use `nixpkgs.config.allowUnfreePackages`.

Both flakes assemble their outputs with the personal-nixpkgs `mkFlake` wrapper and pass the required local library arguments. The root builder's common arguments are `llib` and `rootPath`. The child uses its own `llib` and `lpkgs`. Flake-parts and treefmt-nix are owned through the personal-nixpkgs inputs.

## Native Feature implementations

Every native OS or HM Feature implementation declares its own default-off `features.<name>.enable`. Importing the module makes its options available in that evaluation scope. Its native enablement controls configuration contributions. The Feature registries use the child flake's explicit `nixosModules.<name>` and `homeModules.<name>` exports, with implementations under `pkgs/modules/<name>/{os,hm}/default.nix`. The child owns Nixvim, Niri and sops-nix inputs and composes their upstream modules with the local exports. The Editor and Niri OS exports contribute their package overlays when enabled. Native modules accept actual package values. The root Base consumes the existing child `overlays.share`, `nixosModules.share` and `homeModules.share` exports as common dependencies.

Generic native connections supply defaults for their own options. Greeter derives its session packages from enabled providers, with Niri preceding X11. File-manager HM derives its FileChooser default from the OS File-manager Feature and its FileChooser state, and its Wayfile default from the current HM Niri Feature. Niri HM defaults Noctalia from OS Niri state. HM SOPS can derive its age key path from the actual OS SOPS bridge. Required service and operating-state checks remain native.

## Users and interfaces

A User Registry profile describes reusable personal environment and data. The presence of a System's `users.<uid>` entry constructs the Account. It selects a `profile`, `username`, `homeDirectory` (default `/home/${username}`) and independent HM Features. Its schema exposes account identity, profile binding and HM selections. Native Feature customization goes through the selected consumer module. The Host owns UID reservations and machine authorization. The Account binds a registered UID to its login name and home. Both native account maps use canonical decimal UID strings as keys, and the constructor projects identity using the existing force semantics. Spare Host UID reservations are valid.

## Host facts and graphics

Hosts own stable numbers, UID reservations, authorization, identity, machine resources, WireGuard facts and monitors. The Host FP connection module contributes monitor data to OS Greeter and account HM Niri. A selected Greeter requires a default monitor through its consumer module. HM Niri checks the requirement with its native assertion. A Host without monitors can be valid, including with OS Niri selected. SSH identity lives under `identity.keys`. Root access is separate authorization policy.

## Desktop and native capabilities

Niri remains the main native desktop and starts Noctalia v5 from HM settings. OS Noctalia configuration supplies recommended services without installing its own competing user launch path. Noctalia now owns normal/idle/pre-suspend locking; swaylock remains an allow-when-locked rescue path. One login_box is centered on the default monitor using mode/scale-derived logical dimensions, with weather false and unlock hint true. Custom clock/weather trials were withdrawn; earlier successful migration checks do not verify this final lockscreen stage. Other outputs remain locked; runtime settings may override declarative values.

Greetd's temporary Sway/gtkgreet and the independent IceWM/startx fallback retain separate session duties. Browser reuse across concurrent sessions remains a historical unresolved report. Native xdg.terminal-exec supplies terminal capability; Yazi/Wayfile handle directories and the independent FileChooser portal only affects clients using it. ThinkBook framebuffer initialization is a host-gated oneshot/udev path; kmscon ownership proposals remain unadopted.

## Secrets and agent inputs

Agenix and Agenix-rekey remain Base infrastructure, separate from optional SOPS. The dedicated rage-armored wrapper supports text-only encrypted retention. Master identities unlock repository sources, Host public keys encrypt deployment ciphertexts, and preinstalled Host private keys unlock deployment ciphertexts at runtime. The native SOPS bridge ciphertext lives in `pkgs/modules/sops/os/sops.hm.age`. The OS SOPS consumer derives the bridge's authorized UIDs from Accounts selecting HM SOPS. The User profile owns its SOPS defaults and secret input, and its ciphertext and editing configuration live under `modules/users/lingyu/sops/`.

The User profile maps Pi provider names to SOPS secret names. Its Account consumer resolves those paths in native HM, and both that mapping and the profile's rclone setup guard secret use on the current account's HM SOPS enablement. Agent providers consume runtime paths through their native interface. Static wiring and Agent-without-SOPS evaluation are distinct from live secret-access or multi-account testing.

`modules/base/os/identity.nix` registers the selected Host's non-null SSH identity backup as an Agenix intermediary. Registration is independent of `rootAccess`, which gates YubiKey tooling and pcscd. An intermediary participates in source master-key management. Host rekey skips its backup payload and installs a dummy secret. Backup decryption therefore requires separate verification. Master identity lifecycle ownership and recovery follow-ups remain in [backlog.md](backlog.md).

## Library and verification

`lib/flakeParts.nix` owns the shared FP schema and constructors. `validateAccounts` is internal to construction. `lib/hosts.nix` owns topology, networking and SSH derivation. Libraries receive their actual dependencies individually. Shared Monitor, SOPS secret-input and default-editor value types live in `pkgs/lib/`. Keep Feature-specific wiring in its owner and defer native work until its inputs are available.

`tests/configurations` exercises constructor behavior, schema extension and merge, selection cancellation, unforced unselected deferred modules, independent Accounts, binding invariants, cross-Host and System references, and project connection modules. Host-function checks cover topology, peers, routing, FORWARD isolation and SSH aliases. Root forwards the child native-enable and SOPS-helper checks. Suites use `llib.tests.mkChecks` and `test-overlay.nix` with explicit dependency injection. `tests/default.nix` selects which library namespaces and other dependencies to inject. Treefmt remains part of flake checks. Verification results and their source boundaries are in [current.md](current.md).

## Network ownership

Host topology is derived in FP from the Host Registry using `wireguardRules`, `mkWireGuardNetworkData` and `mkWireGuardTopology`. Base OS projects it into the existing read-only `networking.wireguard.topology`. `mkWireGuardNetworks` takes an explicit `hostName` and returns native networking configuration directly. Its callers obtain topology separately. Hosts own encrypted WireGuard material and stable numbers. One network is derived per endpoint Host. Topology keys are Hub and node Host names, with each Hub's interface, subnet and node IPv4 addresses. Peer roles are per network. Each Hub gives spoke peers individual `/32` AllowedIPs, each spoke routes the network subnet through the Hub, and endpoint Hosts enable IPv4 forwarding. The `wireguard-isolation` FORWARD chain allows IPv4 forwarding within the local Hub's own interface and drops other forwarded traffic involving managed interfaces. Keep this separate from local OUTPUT policy.

SSH targets consume the same topology for system-wide `<hub>.<node>` client aliases. Paths to the same Host share a trusted host key identity. See [current.md](current.md#wireguard-ssh-targets-and-aliyun-reachability) for verification and the Aliyun OUTPUT diagnosis.

## Definition ownership

Define basic shape and validity with types, local and collection invariants with option `apply`, function preconditions where the function consumes them, and final native-state constraints with native assertions. Read-only options constrain raw definitions. Unique types constrain value merging. Give derived facts a clear producer and put fallback interpretation in their consumers. FP modules can extend nested Registry and System/Account schemas and contribute deferred modules using values they own.

## Workload responsibilities

Workloads are explicitly selected native implementations with `workloads.<name>` options. Deployment-specific IPs, ports, interfaces and access values come from FP consumer modules. Root wires Caddy on Aliyun to WBO on ThinkBook at port 18000, with the allowed source and interfaces supplied from FP topology. The native WBO port is required. The Caddy implementation still supplies its interface-wide OUTPUT policy. Configured endpoints do not establish deployed reachability.

Keep Workloads portable by supplying explicit network endpoints and access requirements. A Workload can consume Host infrastructure, declare its own constraints and cooperate with other Workloads. The adopted firewall design requires the Host to own its default egress policy. Distinguish bidirectional data flow from an actual evaluation dependency cycle. The remaining firewall requirements are in [backlog.md](backlog.md#deferred-wireguard-firewall).

## Virtualization and host resources

ThinkBook integrates a declarative libvirt Windows guest through NixVirt, with domain/network/storage XML templates, GPU SR-IOV, guest tooling and Samba sharing. Display experiments return to SPICE after GTK trials; virtualized Windows is a host-owned workload/resource rather than another NixOS host profile. Mount policy distinguishes Windows and shared filesystems, with the Windows partition mounted read-only at this horizon. Static configuration does not establish a successful guest boot, GPU assignment, filesystem safety under every external OS or runtime display result.

## Local packages and tools

Package overlay.nix and test test-overlay.nix sources use an outer attribute-set constructor returning a standard Nixpkgs overlay, commonly {}: final_: prev_: {...}. The owner standardized the two overlay parameter names as final_/prev_; static comparison of the ten changed paths found only identifier/whitespace changes. The shared loader supplies only declared extraArgs/descendantOverlay constructor parameters and rejects other names. Returned overlays remain ordinary Nixpkgs extensions. Test mkChecks.args is the separate test-scope/callPackage dependency environment and is not constructor extraArgs. This is the committed constructor protocol; static source/documentation review does not establish successful checks of the constructor migration.

The pkgs/ child flake owns application input declarations, the local library extension entry and recipes under pkgs/pkgs/. Its dependency versions for root consumption are recorded in root flake.lock; pkgs/flake.lock is no longer tracked. The committed .gitignore allowlist is anchored at the repository root; !/flake.lock permits only the root lockfile, while pkgs/flake.lock remains ignored by the default * rule. An unanchored !flake.lock would also permit child lockfiles. Standalone child use may produce a local lockfile, but the repository supplies no separate committed child lock baseline. Distinct root/child input declarations and versions do not require two committed lockfiles. Its personal-nixpkgs input supplies the generic library; mergeAttrsRecursive with allowOverrides = false combines that library and pkgs/lib/default.nix, which provides shared value types, into child llib. The former local pkgs/lib/packages.nix is removed.

pkgs/pkgs/default.nix requires only child llib and uses llib.packages for overlays and OS/HM module collection. The locked grouped-overlay API takes overlayFile = overlay.nix and two groups: legacy includes all local recipes with export = true, exposing pkgs.legacyPackages when applied; share excludes rage-armored. The default group/output is removed. Child outputs are overlays.legacy, overlays.share (local recipes except rage-armored, plus GAW/Lean/Zotero), overlays.editor, share OS/HM modules and the explicit native Feature modules described above. Root local-nixpkgs references path:./pkgs. Root perSystem configures nixpkgs.overlays = [ inputs.local-nixpkgs.overlays.legacy ], consumes the mkFlake-provided pkgs, exports legacyPackages = pkgs.legacyPackages and shares pkgs with checks, devShells and agenix-rekey. The latter directly uses pkgs.rage-armored. The child no longer explicitly instantiates or exports legacyPackages in perSystem. Standalone child use has its own input declarations. When root consumes the child, the child Nixpkgs input follows root Nixpkgs. Root Base composes the share overlay and native share modules, and Systems and Accounts select their Feature exports.

Root lib no longer owns package discovery. Pure customizations of upstream codex, difftastic and pi-coding-agent live directly in their overlay.nix files, reading upstream packages from prev_ and dependencies from final_; their former package.nix files are removed. Independently named packages retain their recipes, including rage-armored, and Wayfile also exposes a recipe directly consumed by its HM module. Package resources supply composable agent context and shared skills. Pi's offline startup wrapper preserves package layout; it does not prohibit model API networking. Codex's committed wrapper PATH includes bubblewrap plus Python/PyYAML support. Skill instructions do not replace execution authorization. Pi resource extensions and a historical proposed Git-action filter are different capabilities; the latter was not established as implemented by its source.

The child overrides `inputs.personal-nixpkgs.inputs.local-nixpkgs.url` with the GitHub repository source and `dir=pkgs`. The nested relationship is a subdirectory flake depending on personal-nixpkgs, whose own local-nixpkgs input references its repository's `./pkgs` subdirectory flake. The owner reported incorrect resolution of that nested relative path against the process working directory; the explicit Git source is a workaround, not a change to Nix's resolver. Root local-nixpkgs remains path:./pkgs. The lock graph records the Git source's subdirectory and revision. The reported failure and effectiveness of the workaround have not been independently reproduced by the agent.

The child Emarccs input is pinned to c54849019abba42bb5feeabd71548958fe0f0407. Its only local follows override is nixpkgs; flake-parts, treefmt-nix and personal-nixpkgs use Emarccs's upstream declarations. Desktop Emacs service packages use pkgs.emarccs-pgtk, while programs.package uses pkgs.emacs-pgtk; that updated service attribute has not been independently evaluated by the agent. Child lem, nixvim, git-agent-workflow and lean4-nix follow personal-nixpkgs/flake-parts. Root agenix-rekey and nixos-anywhere follow root personal-nixpkgs/treefmt-nix. Root enables treefmt.flakeCheck and excludes *.patch, .gitignore, LICENSE, README.org, flake.lock and *.age. Local explicit formatter-program declarations and direct treefmt module imports were removed during the mkFlake migration. The owner identified the five committed XML-template formatting changes as treefmt-generated; that report does not establish successful Nix checks. Root forwards the child's native-enable and SOPS-helper checks. This architectural description covers committed input declarations and lock state. The old Clash geodata/cache ambiguity remains an unconfirmed historical diagnostic, not a current verified failure or proven fix.

## Static constraint ownership

Host Registry `apply` checks global number uniqueness. Local `apply` checks monitor name uniqueness, at most one default with a mode, canonical UID keys matching their values, and WireGuard endpoint/listen-port consistency. Host number is a stable identifier and must be available to the Registry check without re-reading the final Registry through that same check. Local fields may read other entries. `checks.host-registry` explicitly forces constrained data for all Hosts, including unselected ones. Construction forces System selections and Account binding contracts, including UID registration, minimum Account UID 1000, unique login names and absolute home directories. Keep the remainder of the FP configuration and unselected deferred modules lazy.

The FP connection modules depend on the registered Feature names they extend. Removing an export requires adjusting its connections. Disabling a registered selection leaves those deferred contributions unimported. Keep native assertions for final dependencies such as Noctalia's actual services, Greeter's session packages, and HM SOPS, provider and terminal requirements. Neither construction checks nor flake checks alone establish deployed behavior.
