# Architecture and design constraints

## Purpose and composition

The committed project defines nixos (ThinkBook), nixos-matebook, nixos-server (Aliyun) and nixos-wsl. Its goal is selectable shared user capabilities over distinct platform/hardware environments, with finer ownership than one monolithic HM profile. Root flake-parts options own final enablement, UID binding and external input/module/overlay adaptation. The current framework organizes Hosts, Users, Features and Workloads through a largely uniform category and assembly protocol. Explicitly enabled Share supplies common OS/HM behavior. Modules check dependencies without silently enabling peers. The owner sees value in sharing these mechanisms and has retired category parity in system construction as a long-term design principle.

Module descriptors are discovered from OS/HM implementation entry points and reject nested modules. Optional root default.nix holds cross-implementation coordination. moduleRegistry separates static metadata and external integrations; nixosBuilder and llib.flakeParts.mkNixosConfigurations construct the output collection. The typed adapter resolves only declared functionTo/submodule values. Configuration/metadata fields must be disjoint. OS config.modules is the merged internal readOnly view; HM consumes osConfig.modules.

## Construction semantics and layer boundaries

Hosts provide infrastructure required by every system closure, with exactly one selected Host per system. Features describe composable capabilities. Users describe people or accounts deployed on a system and their environments. Workloads describe deployable, movable and cooperating services or tools. Share's existence and construction semantics need review. These differences in responsibility, presence, cardinality and dependencies can warrant category-specific construction protocols while reusing discovery, option construction, metadata management and implementation assembly.

Prefer expressing fundamental structure and responsibilities in the construction protocol so invalid shapes are harder to represent. Keep validation for global consistency, cross-object relations, library preconditions and constraints on final NixOS state. Judge changes by the constraints they express and where the relevant inputs are available. The current Host protocol permits independent `enable` values, validates that exactly one Host is enabled and uses a getter to recover it. Direct construction with a single selected Host is a research direction with its API still open.

The current split reflects the incremental introduction of the flake-parts module system onto an existing module structure. The review should distinguish the global static infrastructure model, per-system construction and local plans, and implementation requiring final NixOS evaluation. WireGuard topology is a candidate for derivation in flake-parts. NixOS remains the natural place for service configuration, actual UIDs, resolved secret paths, interface configuration and nftables rules. Assess static computations and `functionTo` uses individually based on their real dependencies and responsibilities. The research and open interface decisions are in [backlog.md](backlog.md#module-system-architecture-refactor).

## Module directory interface

Root and child flakes use personal-nixpkgs.lib.mkFlake inputs.nixpkgs to assemble flake-parts configuration. Each passes a configuration callback receiving lib, imports its local library with that argument and sets moduleLocation = __curPos.file. Root supplies llib and specialArgs.rootPath; the child supplies separate llib and lpkgs. Both personal-nixpkgs inputs follow their respective Nixpkgs inputs, while flake-parts/treefmt-nix are owned by personal-nixpkgs rather than directly declared root/child inputs. The root and child personal-nixpkgs nodes are separately recorded in root flake.lock and currently pin the same revision. This is static call-site/lock evidence, not fresh Nix evaluation of the wrapper.

Module-related library APIs receive the physical module directory as modules, rather than repository root/modulesDir pairs or an assembly rootPath. discoverModules modules returns descriptors whose logical path starts with [ "modules" ], independently of the directory basename or repository location. The module/os/hm descriptor fields retain actual filesystem paths. Declaration and validator loaders resolve files beneath modules after removing the logical prefix; categoryModules locates category default.nix beneath the same directory. Module recognition, nested-module rejection, declaration interfaces and validator ordering/deduplication retain their prior rules. See lib/modules.nix, lib/flakeParts.types.nix, lib/flakeParts.validators.nix and lib/flakeParts.configurations.nix for implementation entry points.

The Configuration type nixosConfigurations explicitly accepts modules, llib and registry. It obtains metadata directly from registry and constructs the existing declaration context internally, exposing that input as moduleRegistry alongside lib/llib/config/options. The earlier optional scope parameter hid this required metadata dependency and is superseded. FunctionTo adaptation still needs its runtime scope; builder.specialArgs.rootPath is a separate context and is not removed by narrowing the directory interface. This separates filesystem location from logical option paths and lets tests consume only modules without reconstructing a repository root. The directory-interface fixture verifies the intended contract using a physical directory whose name is not modules; its presence does not establish that the test has been executed.

## Native Feature implementations

The committed native contract exposes a default-off `features.<name>.enable` in each actual OS/HM implementation. Module imports make options available. Native enablement controls contributions independently in each scope. The current root Registry sets enable explicitly as part of delivery until the root construction model is revisited. The SOPS bridge ciphertext belongs to the native SOPS feature, while Agenix and Agenix-rekey remain root Share infrastructure. See [current.md](current.md#committed-phase-one-native-interfaces-and-sops-ownership) for the implementation and validation state.

The child flake discovers and exports Feature entries as native `nixosModules.<name>` and `homeModules.<name>` modules. The path convention is `pkgs/modules/<name>/{os,hm}/default.nix`. The child composes its upstream Nixvim input with the local Editor implementation under `homeModules.editor`. The root Registry retains control of external integration, overlays, FP-to-native configuration mapping and UID allocation. Root Feature entry markers preserve discovery and availability. Agent and SOPS retain root HM compatibility declarations for User profile inputs. Native Feature modules declare their own required `features.<name>` options and accept actual package values. Shared Monitor, SOPS secret input and default-editor value types live in `pkgs/lib/` and enter the root type namespace through the root flake. Defaults and definition-presence semantics remain local to each option declaration.

## Users and interfaces

Directory-named user profiles retain unique bound UID and host-subset constraints. Outer configuration chooses user identities and Feature allowUidList. The builder sends user HM implementation to the bound UID and Feature HM implementations/external homeModules to recipients; other kinds contribute through sharedModules. Per-user interfaces and OS internals remain declaration mechanisms distinct from implementation enablement. Parent disablement prevents implementation/external integration loading; a child switch does not independently activate its parent.

## Host facts and graphics

Static metadata facts are available independently of activation. Exactly one host must be enabled; a strict getter remains the query interface, while the Hosts FP configuration validator enforces cardinality at the per-system apply boundary. The earlier native tryEval-based assertion is removed by phase 2.3. Hosts own numeric UID registries, identity, boot/shared resources, WireGuard facts and monitor data. Enabled users need registry membership, while spare UID slots are valid. Monitor names are nonempty/unique, at most one is default, and enabled graphical consumers impose the stronger default-monitor requirement. Default monitors require a mode for coordinate derivation. SSH identity is under identity.keys; rootAccess is separate policy, not a synonym for knowing a host public key.

## Desktop and native capabilities

Niri remains the main native desktop and starts Noctalia v5 from HM settings. OS Noctalia configuration supplies recommended services without installing its own competing user launch path. Noctalia now owns normal/idle/pre-suspend locking; swaylock remains an allow-when-locked rescue path. One login_box is centered on the default monitor using mode/scale-derived logical dimensions, with weather false and unlock hint true. Custom clock/weather trials were withdrawn; earlier successful migration checks do not verify this final lockscreen stage. Other outputs remain locked; runtime settings may override declarative values.

Greetd's temporary Sway/gtkgreet and the independent IceWM/startx fallback retain separate session duties. Browser reuse across concurrent sessions remains a historical unresolved report. Native xdg.terminal-exec supplies terminal capability; Yazi/Wayfile handle directories and the independent FileChooser portal only affects clients using it. ThinkBook framebuffer initialization is a host-gated oneshot/udev path; kmscon ownership proposals remain unadopted.

## Secrets and agent inputs

OS age/agenix-rekey is shared infrastructure, separated from optional SOPS so its tooling builds/downloads need not block base secret deployment, using encrypted host material and separately configured master identities, including YubiKey support. The dedicated rage-armored wrapper satisfies text-only encrypted retention for rekey operations. Optional per-user SOPS remains an application/HM Feature; the shared age key bridge is exposed through age.secrets with group access and user-derived membership. Agent providers consume file paths independently of secret manager and enable only explicitly selected providers. The reconstruction did not decrypt material or verify private-key custody or deployed runtime access.

Host identity backups are registered by modules/hosts/identity.nix from the enabled Host metadata's non-null identity.keys.ssh.private.key as age.secrets.ssh-identity with intermediary = true. Registration is independent of rootAccess; that flag gates YubiKey tooling/pcscd only. The upstream intermediary mechanism includes the repository source in master-key management while skipping real host rekey/deployment and installing a dummy secret. Current source ciphertexts include ordinary age and YubiKey-compatible recipient stanzas. Master identities unlock repository sources; Host public keys encrypt deployment ciphertexts; preinstalled Host private keys unlock those ciphertexts at runtime. A Host rekey success does not validate an intermediary backup. No secret-management FP option migration or virtual management node is adopted; moduleRegistry.share has no framework-defined global policy meaning.

## Library and verification

Owner-adopted construction rule: library imports must receive their actual dependencies individually. Do not normalize flakeParts construction in lib/default.nix by recursively passing the whole llib, or by rebuilding a broad llib aggregate as a substitute for explicit dependencies. Each imported file should declare the dependencies it actually consumes; identical constructor signatures are not a goal. This rule concerns construction-time wiring, not a blanket prohibition on established evaluation-context interfaces. The proposed recursive whole-library injection was rejected, not adopted. The committed refactor implements this rule for all three flakeParts imports: configurations receives lib/discoverModules/mkOptionTree, validators receives lib/discoverValidatorFiles, and types receives lib/mkOptionTree/mkOptionModules/mkOptionName. Runtime mkValidatorApplications and the Registry type receive required llib arguments from their callers, keeping declaration/validation context separate from constructor dependencies.

Use lib/modules.nix for discovery/schema trees, lib/flakeParts.configurations.nix for adaptation, private declarations, HM delivery and constructors, lib/flakeParts.types.nix for registry/builder types, lib/hosts.nix for host/network derivation, pkgs/modules/sops/hm/secrets.nix for native SOPS secret generation and the personal-nixpkgs input library for child-project package discovery. modules/_options.fp.nix and category/module FP declarations define outer configuration and metadata; OS/HM declarations use their environment-specific filenames. New builder UID aggregation replaces the retired prepend helper, so its old fixture is historical evidence rather than a current API invariant.

Tests and treefmt are registered in flake checks. The committed test organization uses test-overlay.nix suite entries and explicit parameter injection. The committed locked-library API adaptation is: root llib.tests.mkChecks discovers/composes overlays and assembles its independent scope internally, taking root, overlayFile and explicit args (lib, modules, runCommand and selected library namespaces). It no longer exports mkOverlays or accepts caller scope. The root tests import passes lib, pkgs, llib and modules = ./modules. tests/default.nix owns selection/flattening of library dependencies and injects only runCommand from pkgs into the suite context. Explicit library dependencies use flattened lower-camel aliases (llib.name.name -> llibNameName, converting hyphens too). Useful first-level namespaces may be passed as llibFlakeParts, llibModules, etc.; suite overlays map those aliases back to ordinary names (moduleLib for the module-library namespace, distinct from the modules directory) before callPackage, preserving namespace.member calls in test bodies. The whole llib is accepted only at the aggregate boundary, not passed to individual suites or the test scope. Existing FP declaration protocol contexts remain named llib and contain only their required types namespace. Each suite entry now calls its own test.nix through final.callPackage (the final rename and dependency narrowing are committed but not yet execution-validated); existing assertions and check names remain. Root consumes only the external tests namespace, separately from the child's packages namespace and locked version. Dependencies outside a test directory must enter through function parameters: parent-relative dependencies such as ../* and ../../*, including repository-root path literals, are prohibited. Local child fixture paths remain valid. Actual-module tests now receive modules directly; the earlier deferred rootPath narrowing is complete. The API-only adaptation passed an authorized root flake check after a one-line args formatting correction. Later renaming/dependency refinements are committed together with that API adaptation and lock update; the final combined tree has not been checked with Nix by the agent. The reconstruction statically inspected committed implementations, tests, history and documentation; it did not run those project checks. Original working-tree provenance, some early design conversations and runtime results remain incomplete. Final lockscreen/portal/renamed declaration/share-disabled behavior are not upgraded from old successful checks to fresh verification. Browser session reuse, geodata precedence and multi-VT console ownership are historical open investigations requiring present reproduction before treatment as current defects.

## Network ownership

Hosts own encrypted WireGuard material and stable numbers. `lib/hosts.nix` derives one network per endpoint Host and keys the topology by Hub and node Host names. The read-only NixOS topology exposes each Hub interface name, subnet and node IPv4 addresses. Roles are per network, addresses use stable Host numbers, and a Host without WireGuard needs no WireGuard key path. Each Hub configures spoke peers with individual `/32` `AllowedIPs`. Each spoke uses that network's subnet as the Hub peer's `AllowedIPs`. IPv4 forwarding is enabled on endpoint Hosts. The `wireguard-isolation` nftables FORWARD chain allows IPv4 forwarding within a local Hub's own WireGuard interface and drops other forwarded traffic involving managed WireGuard interfaces. It is independent of local OUTPUT policy. SSH targets consume the same topology for system-wide aliases and trusted Host identities. See [current.md](current.md#wireguard-ssh-targets-and-aliyun-reachability) for verification and the Aliyun OUTPUT diagnosis.

## Definition ownership

Internal marks producer ownership rather than confidentiality. ReadOnly constrains raw definitions, while unique types constrain value merging; they are not interchangeable. Remove producer defaults that would conflict with the sole final definition, keep element-level uniqueness where needed and put fallback interpretation in consumers. User UID is an explicit final-composition input; host UID metadata is produced internally. Review the complete index: a check of a working tree cannot prove a different staged snapshot.

## Workload responsibilities

Workloads describe services and tools selected by deployment configuration. The current deployment wires Caddy on Aliyun to WBO on ThinkBook in `flake.nix`. Each consumes explicit network settings, including WBO's permitted source. Declared `functionTo` values defer access to resolved system networking until the adapter resolves the inputs for OS consumers. WBO's port defaults to null and this deployment explicitly supplies 18000. The current Caddy module also installs the interface-wide OUTPUT rule described in [current.md](current.md#wireguard-ssh-targets-and-aliyun-reachability). The wiring establishes the configured endpoints. Deployed HTTP reachability requires runtime evidence.

Preserve Workload portability by letting deployment configuration wire explicit endpoints. A Workload can consume Host networking, declare required access and its own deployment and security constraints, and depend on other Workloads. A Workload's enablement should leave the Host in control of its default egress policy. Hosts are mandatory infrastructure, so bidirectional data flow between Hosts and Workloads alone does not justify a top-level Networking category. Check whether the concrete evaluation dependencies form a cycle. Future flake-parts composition could express deployment relationships and service connections directly. Workload instances, an explicit dependency protocol and configuration schema remain open.

## Virtualization and host resources

ThinkBook integrates a declarative libvirt Windows guest through NixVirt, with domain/network/storage XML templates, GPU SR-IOV, guest tooling and Samba sharing. Display experiments return to SPICE after GTK trials; virtualized Windows is a host-owned workload/resource rather than another NixOS host profile. Mount policy distinguishes Windows and shared filesystems, with the Windows partition mounted read-only at this horizon. Static configuration does not establish a successful guest boot, GPU assignment, filesystem safety under every external OS or runtime display result.

## Declaration registration

Private functions in `lib/flakeParts.configurations.nix` register OS internal declarations and each user's HM interfaces independently of `share.enable`. Share provides common behavior, while declaration availability does not activate an implementation. This keeps the aggregator outside discovered declarations, avoiding the earlier self-import failure.

The repository loader uses three environment-specific interfaces:

- `_options.fp.nix` along module path prefixes returns outer configuration/metadata schema branches.
- `os/_options.os.nix` is a native NixOS declaration module.
- `hm/_options.hm.nix` returns an HM interface fragment parameterized by module name and evaluation context.

`_metadata.fp.nix` stores static values under the committed metadata filename convention; `_metadata.nix` is retired without a compatibility fallback. Metadata files return ordinary attribute sets, not flake-parts modules. The committed `_validators.fp.nix` protocol is described below; the committed phase 2.3 migration assigns production static constraints to their owning directories. The suffix identifies interpretation environment, without imposing one namespace or function signature. This is a repository convention, with no old-name fallback, rather than native automatic loading. The declaration-file renames were byte-identical with paired loader/documentation changes; reconstruction did not establish a final evaluated check or share-disabled behavior test. Later worktree checks are recorded in [current.md](current.md); a dedicated share-disabled test remains unestablished.

## FP validator protocol

`lib/modules.nix` discovers `_validators.fp.nix` through descriptor prefixes, deduplicating and sorting root/category/module owners by depth and path. OS/HM implementation directories are excluded. After the committed context refactor, files are ordinary `{ path }` functions returning optional `metadata` and `configuration` predicates. Only owner path is passed at import; lib and caller-supplied llib are passed at branch execution. The earlier protocol passed lib/llib at import; that design is superseded. Metadata receives the merged Registry. Configuration receives name, merged per-system configuration and evaluated Registry. Predicates return booleans, may assert/throw specific errors and do not transform input values. Unknown branches, invalid structures and non-boolean results fail.

`lib/flakeParts.validators.nix` supplies `llib.flakeParts.mkValidatorApplications`. The small top-level apply integrations in `flake.nix` reuse its Registry identity validator and per-system lazy mapper. It composes constraints with conjunction rather than overriding functions and supplies file/branch/system error context. Registry validation never reads systems; configuration validators must use their supplied unprocessed input, not recursively recover it from top-level FP config. Only relevant fields and predicate booleans are forced. Actual typed-default tests and unrelated-value traps are essential: neither deepSeq of whole inputs nor early invocation of functionTo values is permitted. Phase 2.3 supplies seven meaningful production validator files without placeholders. Their ownership and retained native boundaries are described below. See [current.md](current.md) for test evidence and the working-lockfile validation boundary.

Generic-library `assert`/`throw` checks protect framework invariants and function preconditions: discovery root-module/nesting restrictions, valid option-tree paths and disjoint top-level configuration/metadata fields in the adapter. They remain in their implementing libraries, rather than being moved into optional module-local business validators merely because they use assertions. Final NixOS/HM-state assertions remain native for a different reason: their evaluated data is outside the FP static boundary.

## Static constraint ownership

The migration is committed; [current.md](current.md) distinguishes its earlier worktree checks from the committed and newer working dependency states. Hosts `_validators.fp.nix` has two branches: metadata checks all Hosts for unique numbers, per-Host monitor constraints, canonical decimal UID keys/values and WireGuard endpoint/listenPort consistency; configuration requires exactly one enabled Host. User configuration validation joins configuration enablement with selected-Host Registry UID registrations. Enabled Users need assigned unique UIDs, unique usernames and absolute homes; every assigned UID is at least 1000, including disabled Users. Membership is a subset check, preserving spare Host registrations. Invalid Host cardinality is left to its owner rather than causing incidental lookups.

Feature configuration validation checks duplicate/unknown allowUidList entries only for enabled Features with an HM implementation, preserving disabled default recipients and OS-only behavior. Niri validates child-parent requirements, Waybar/Noctalia exclusion and its selected Host default-monitor requirement. Greeter validates only its static default-monitor requirement. Proxy validates all four child-parent requirements and only clash-verge/mihomo exclusion. ThinkBook validates flatpak -> host enable. Always-discovered validators make explicit child enablement under disabled parents reject reliably, repairing the former conditional-import gap without enabling dependencies.

Keep Noctalia's actual NetworkManager/Bluetooth/power/UPower requirements in NixOS. Keep Greeter session package mainProgram/provider checks, monitor interfaces, Niri session wrapper/package registration and all HM SOPS/provider/terminal-exec checks native. Host common imports, User account/HM projection and WireGuard generation remain intact. Assertion-only Features, Proxy and ThinkBook root defaults disappear; optional-root assembly already supports their absence.

No new per-rule business test framework or equivalent FP negative fixtures are introduced. The obsolete module-composition suite is removed because all its cases extracted migrated native assertions, including its positive Host-count assertion. Generic validator failure/laziness tests and independent adapter/Host/SOPS/type coverage remain. Valid-system regression evidence does not claim exhaustive invalid-input coverage. The separate tests dependency-injection backlog and issue #2 final audit remain pending.
