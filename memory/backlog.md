## git-maintenance changelog phase one

Adopted pending instruction-only extension of pkgs/pkgs/git-maintenance/src/git-maintenance/references/changelog.md, with minimal necessary routing/baseline/write-scope changes to SKILL.md. The owner's latest phase-one guide supersedes the earlier release-contract discussions where they differ. Keep a Changelog 2.0.0 supplies content conventions; SemVer applies only under the target project's version policy. The Org profile below is an opt-in workflow extension, never a claim that Keep a Changelog mandates these files or a reason to migrate an existing Markdown/other-format project. Preserve valid existing analysis, language/style conventions, commit/readme/top-level audit behavior, standard references, package pins/install checks, license metadata and version policy. Do not implement phase-two scripts, dependencies, CLI, CI, converters, platform calls or release automation.

For projects adopting this profile, root CHANGELOG.org contains a concise, categorized user-facing history and development/candidate entry points, not merely an index; important breaks remain visible there. Each newly released version requires a complete CHANGELOGS/<tag-name>.org before publication. That detailed file is the sole authoritative Release Notes manuscript; root summaries may be shorter but must agree with it, and missing details never permit falling back to the root as a publishing source. Detailed-file internal structure is flexible, with user-visible changes, impacts, breaks, migration, limitations and verified context as needed. A detailed file may exist during preparation and does not prove publication. Old tags must not be rewritten to insert newly backfilled files; report legacy coverage gaps.

Version headline titles express version identity and must not embed hosting-platform URLs, including GitHub Release URLs. Formal named versions use CUSTOM_ID exactly matching the Git tag name; no GIT_TAG property is introduced. Plain version titles are normal, and external navigation links may appear in the body when verified and useful. Root-to-detail links use native file links; internal Org navigation uses CUSTOM_ID rather than persistent line numbers. Platform-generated Release Notes URLs are separate publishing-tool concerns.

Use Org-native file settings: #+TODO: TODO NEXT WAIT | DONE CANCELED; #+STARTUP: logdone; #+PROPERTY: TIMEZONE UTC. Version level 1 normally follows TODO (development, optionally Unreleased or a provisional version), NEXT (human-frozen version and scope, definite CUSTOM_ID, details in preparation), DONE (formal finalization/release marking, reviewed complete details and version CLOSED). Unreleased is an optional temporary name, not a mandatory permanent inbox. WAIT/CANCELED are especially useful for individual items; a paused/canceled entire version is exceptional and must be explained. Lower headings, ordinary lists and checkboxes may mix; six Keep a Changelog types remain the normal level-2 categories, empty ones omitted, and Breaking stays within Changed/Removed. Unresolved, canceled or blocked maintenance items must not accidentally become published change claims.

All existing Org TODO keyword transitions at both version and item levels are human-only in phase one. The agent may suggest transitions and maintain explicitly authorized ordinary content, including NEXT detailed drafts and corrections to DONE bodies, but must not change existing state or existing version CLOSED. Creating an authorized new development entry as TODO is permitted. Authorized history reconstruction may create a new historical DONE entry and derived CLOSED only for a confirmed historical release/tag; it cannot overwrite an existing version's state or time under that exception. Checkboxes may be updated under explicit content authorization, but are no substitute for release authorization. A complete detailed file or completed children do not authorize NEXT -> DONE.

Version CLOSED is a standard inactive Org planning timestamp, such as [2026-10-29 Thu 06:56], interpreted in UTC under this profile; there is no repeated headline date and no %z/%Z inserted into the brackets. TIMEZONE is a declared convention, not an Org mechanism that makes C-c C-t emit UTC. logdone may also close CANCELED entries, so CLOSED alone never proves release: version DONE, complete details and confirmed release evidence are required. For new releases, a human verifies UTC CLOSED at the NEXT -> DONE finalization/release checkpoint; the release tag normally points to the commit containing DONE/CLOSED/details. Do not require CLOSED to equal committer time, manipulate GIT_COMMITTER_DATE, or replace it with platform publication time.

For authorized historical backfill under this Org profile only, use the confirmed old release tag's peeled commit committer Unix timestamp as the uniform reconstruction source: git log -1 --format=%ct '<tag>^{commit}', converted to UTC Org inactive time; compare to minute precision. This is an explicit historical recording convention, not proof of actual historical platform publication time. Do not use tagger timestamps, GitHub published_at or the current backfill time. Unknown/unreliable tag-to-commit mappings leave a reported gap, never a guessed CLOSED. Ordinary historical date uncertainty and the general prohibition on pretending commit timestamps independently prove publication remain intact; explain the profile's reconstruction exception.

History content remains source-first: identify local candidate release trees and distinguish tags from confirmed releases, compare endpoint trees (not merge-base three-dot diffs), examine historical README/interfaces/manifests/tests, and investigate commits only as needed. Existing Release Notes/publication/distribution records supply cross-checks, overlooked information, context and release facts. Prefer retaining verified old wording while organizing it into the appropriate summary/detail content; revise redundant, inaccurate or misplaced content case by case. Do not mechanically reproduce commit logs, invent facts or attribute all capabilities of the first recovered tree as new. A missing GitHub Release is not proof that no release occurred, and working links are not a prerequisite for reconstruction.

Specify future Release Notes sourcing without implementing an extractor: new-profile versions use the detailed file in their own release tag. For legacy tags without it, inspect confirmed successor release snapshots and choose the first containing that version's detail file. Successor order requires the project's confirmed release sequence and Git history relationships, not lexical names, tagger time or assumed linear maintenance branches. Report ambiguity. Only when explicitly allowed, an audited mainline backfill may serve as fallback; identify its exact source revision and reproducibility limits. Retain old platform notes as historical material and never silently overwrite them. Independent later tooling handles extraction, Org export (including excluding property drawers), validation and publishing; none is claimed implemented in phase one.

Keep initialize/update/audit as the only operations. initialize can create authorized root/detail files and historical entries, without implicit HEAD updates; update uses latest confirmed release to HEAD by default (or explicit staged/worktree evidence), maintains the current TODO version without requiring a literal Unreleased title, and edits NEXT/DONE content only within authorization and state restrictions. audit is read-only and checks categories, summaries/details consistency, completeness, IDs/names/tag relations, UTC CLOSED (using the historical convention when applicable), navigation and unfinished publication blockers. Report specific evidence, limits and recommendations, not fictitious mechanical guarantees.

Write scope must explicitly cover the authorized root CHANGELOG plus selected CHANGELOGS/<version>.org files; it never includes README, manifests, configuration, Git index/history or hosted assets. Preserve staged/worktree edits and clarify genuine conflicts. After creating each file, diagnose ignore coverage with read-only git check-ignore -v --no-index -- <path>; report the matching rule and a separate suggested fix without modifying .gitignore or staging. Search large histories by bounded version/CUSTOM_ID/path queries before selective reading. Only authorized CHANGELOG writes are allowed; audit/drafts authorize none, and no Git publication operations are delegated to the agent.

Manual acceptance must cover existing Markdown without migration; fresh Org settings; unnamed and provisional TODO versions; content edits to human-created NEXT without transitions; missing mandatory details blocking a sufficient-release assessment; verified DONE facts without state edits; mixed WAIT/CANCELED/checkbox content; confirmed-tag historical time derivation; legacy successor-snapshot discovery and ambiguity; old-note/source conflicts and useful wording retention; optional body navigation URLs; ignored new files; read-only audits/drafts; preservation of user edits; and explicit evidence/coverage gaps. First phase must be independently usable without scripts. Delivery must distinguish actual edits and manual verification from unimplemented conversion/publishing guarantees.
