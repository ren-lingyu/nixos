## Feature wiring and native option interfaces

The owner adopted the constraints below for a pending refactor. They describe target behavior. The isolated evaluation is complete; the production patch and its verification are pending. See [current.md](current.md#root-feature-implementations-and-wiring-preparation) for committed state and experimental evidence.

- FP owns reusable Registry objects in `nixosBuilderArgs` and the resolved System and Account composition in `nixosConfigurations`. All native Feature contributions enter the selected System or Account `features.<name>.module` as deferred modules. Retain the roles of `mkNixosSystem`, `mkAccountModule` and `selectedModules`. Keep the removed discovery and native mirror out of the design.
- Keep the User profile's existing `name` and general `module`. Add sparse `features.<name>.module` entries with no Registry-side enable flag. Each module is read-only with no default and uses `llib.types.featureModule`. Accept attrsets and functions, normalize to a callable value, preserve function argument requirements, and accept explicit imports where file splitting is needed. The function returns definitions beneath its own native Feature namespace. This is a data-wiring convention, with no separate evaluation scope, filtering, origin tracking or security isolation. The candidate wrapper uses `lib.setFunctionArgs` and `lib.functionArgs`; the isolated evaluation confirmed its mechanics for the tested inputs.
- Generic FP wiring contributes the User module to the referencing Account's HM Feature deferred module. Native selection remains the Account's responsibility. Account evaluation remains isolated even when profiles are reused. Limit the mechanism to User-to-HM. Move SOPS defaults/input and Agent provider configuration out of dedicated User FP business options. Native Features retain the data types, merge rules and validation. Move the existing Host monitor wiring to Greeter and Niri and Account-derived OS authorization to SOPS. Retire the centralized Host/User files once empty.
- Treat native business configuration, internal wiring and derived outputs separately. Use read-only for internal inputs and derived outputs where appropriate, with ordinary native omission semantics. Keep existing valid configurations and explicit System/Account overrides. Avoid internal marker conventions, mirror namespaces, new data containers or checks for whether data is worth supplying. Check HM-to-OS dependencies against the actual consumed interface or state. No Feature activates, imports or configures another Feature.
- Greeter consumes the complete typed default Monitor as read-only input and exposes read-only `sessionPackages`, retaining Niri before X11. Niri HM receives complete read-only monitors; Niri and X11 retain read-only `sessionPackage`. OS Noctalia defaults with OS Niri enablement, HM Noctalia defaults from OS Niri and OS Noctalia, and HM Waybar defaults on when HM Niri is enabled without HM Noctalia. Keep OS and HM business settings independently selectable.
- File-manager retains OS and HM FileChooser controls, with OS defaulting with OS File-manager. Keep the HM FileChooser default from OS File-manager and its FileChooser state and independent HM Wayfile default from HM Niri. Shell restores read-only `bash.package` and `zsh.package` and updates actual consumers. HM Shell depends on the consumed package interfaces and native program state, independently of the OS Shell enable flag.
- OS SOPS owns read-only `authorizedUids` with one FP producer and resolves UID-to-login through native Accounts. Restore read-only `features.sops.ageKeys.hm.{name,path}`: OS owns the secret name and uses it to register and locate the bridge. Enabled HM SOPS requires OS SOPS and reads that published path through `osConfig`; remove HM `ageKeyPath`. Keep optional read-only `defaultSopsFormat`, `defaultSopsFile` and `secretsInput` with their current types. A shared-key-only setup, explicit empty input and the existing `lingyu-minimal` selection stay valid; nonempty secret generation retains its data requirements.
- Agent keeps provider shape, independent enable and `apiKeyFile` fields and the enabled-provider credential requirement. Internal fields are read-only and can be omitted independently across providers. Agent accepts non-SOPS credentials. A User may use current HM SOPS state and a native secret path in their own Feature module; prefer one `mkIf` at `pi.providers` over per-field guards.
- Defer per-User SOPS ciphertext or keys, further authorization changes, unrelated Host Registry consolidation, stronger configuration-origin or path checking, and existing independent backlog.

## Deferred WireGuard firewall

The owner adopted these constraints for design and acceptance. The current Aliyun policy and decision to defer a local change are recorded in [current.md](current.md#wireguard-ssh-targets-and-aliyun-reachability).

- Aliyun defaults to denying locally initiated connections over managed WireGuard networks. Policy belongs to the Host and is independent of the Hub topology role and whether Caddy is enabled. Allow the return traffic required by permitted inbound connections.
- Workloads may declare required access and their own security constraints. Apply Caddy's restrictions across every managed WireGuard interface. Caddy may initiate access only to the designated upstream through the designated interface. Adding a managed interface grants Caddy no additional initiation privileges.
- Decide Workload principal identification and isolation mechanisms case by case. The scope is managed WireGuard access control. General Internet/LAN egress control and a complete Workload network sandbox are outside this scope.
- Keep WireGuard forwarding isolation distinct from locally generated OUTPUT policy. Preserve Workload portability.

Earlier local rule interfaces, separate nftables tables and conntrack drafts were exploratory. The completed composition refactor retained the existing Caddy OUTPUT policy. Evaluate a separate design when authorized. No post-refactor private SSH or ICMP test is established.
